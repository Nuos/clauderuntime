0. 引用起点与归档范围

引用起点：

LLM / Context / AgentLoop / ToolRuntime / Policy / State / Execution Environment

那么 Claude Code 真正值得继续拆的，恰恰不是再增加几个“同级核心模块”，而是研究一批横跨这些模块边界的 Cross-Cutting Harness / Runtime Mechanisms（横切式运行机制）。

论文最新版 v2 也把重点说得很清楚：核心 loop 只是简单的 model → tools → repeat；大量工程复杂度存在于外围的权限、五层 compaction、扩展机制、subagent orchestration、session storage 等系统。论文项目进一步直接称 hooks、classifier、compaction、isolation 为难以复刻的 cross-cutting harness。

我建议把它们整理成下面 14 类关键辅助机制。
主要研究依据：论文《Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems》（arXiv:2604.14228）及 Claude Code 源码镜像仓库 Nuos/claude-code-claude-code-source-code-full。

1. 七大核心模块之外：Cross-Cutting Runtime Mechanisms

如果沿用七核心模块：

LLM / Context / AgentLoop / ToolRuntime / Policy / State / Execution Environment

那么真正值得继续拆的，不是再增加几个“同级核心模块”，而是一批横跨模块边界、控制数据流 / 权限流 / 状态流 / 执行流的横切机制。

1.2 机制一：Hook Runtime — Lifecycle Cross-Cutting Extension

Hook Runtime 不属于 LLM、Context、AgentLoop、ToolRuntime、Policy、State、Execution Environment 中任何一个单一模块，它横切整个 Runtime 生命周期：

SessionStart
     │
UserPromptSubmit
     │
LLM
     │
PreToolUse
     │
PermissionRequest
     │
Tool Execution
     │
PostToolUse
     │
Context
     │
Stop
     │
SessionEnd

它把生命周期位置、事件协议、handler 注册、匹配、执行、聚合、timeout、async、blocking 结果等统一起来。因此 Hook Runtime 是第一类典型 Cross-Cutting Runtime。

1.3 机制二：Authorization Pipeline — 授权决策流水线

Policy 回答“规则是什么”；Authorization Pipeline 回答“一次真实 Tool Action 到底经过哪些检查、以什么顺序形成最终执行决策”。

Tool Pre-filter
      ↓
PreToolUse Hook
      ↓
Deny-first Rule Evaluation
      ↓
Permission Handler
      ↓
Execution
Policy = Rules
Authorization Pipeline = Policy Evaluation Runtime

它真正位于 ToolRuntime ↔ Policy ↔ Execution Environment 之间。

1.4 机制三：Context Shaping Pipeline — 上下文整形流水线

Claude Code 的 Context 管理不是一个压缩函数，而是五层渐进式流水：

      ↓

      ↓

源码 query.ts 中对应 applyToolResultBudget → snipCompactIfNeeded → microcompact → contextCollapse → autocompact → LLM API。它决定“上下文过长时，系统如何仍能持续推理”。

Claude Code 支持在 tool call 仍由模型 stream 逐步生成时，就进入工具调度；同时也保留非 streaming 的 runTools() 路径。

3. 用户对初版图的明确反馈

用户原始反馈：
“非常不合格！！（1）图中 Policy与 Authorization 有什么区别，是不是重复、重叠了？？？（2）模块一、四、毫无意义而且重复！（3）中间的大循环是什么含义？阐释图的原要求是什么？？（4）怎么才9种机制”

该反馈实际提出了四个必须修正的架构表达问题：

  1. Policy 与 Authorization Pipeline 必须严格区分：Policy 是规则本体 / 决策语义；Authorization Pipeline 是把 tool intent 经过过滤、hook、permission evaluation、policy decision 最终落地为执行决策的 Runtime 流水线。
  2. 核心模块展开不能重复：每一个展开框必须说明内部结构、作用、输入 / 输出，而不是把中央主轴内容换一种说法再重复一遍。
  3. “大循环”必须命名和解释：它不是一个业务模块，而是跨轮反馈回路：结果沉淀 → 状态持久化 → 上下文重建 / 整形 → 下一轮模型推理。
  4. 横切机制必须完整：不能只在图上选 9 种；需要明确呈现 14 类横切机制总表。

5.11 Permission：Mode 与 Behavior 两套分类

源码外部 permission modes：

acceptEdits
bypassPermissions
default
dontAsk
plan

内部还存在：

auto
bubble

而单次 Action 的 Permission Behavior 则是：

allow
deny
ask

Permission Mode = 系统所处的信任 / 自治工作模式；Permission Behavior = 某一个具体 Action 的最终裁决。
