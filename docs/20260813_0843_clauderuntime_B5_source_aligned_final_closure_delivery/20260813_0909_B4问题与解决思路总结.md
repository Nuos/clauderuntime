# ClaudeRuntime B4：问题、根因与解决思路总结

> 文档定位：记录 B4 开发过程中实际暴露的问题、已经采用的解决方式、仍然存在的缺口，以及进入 B5 后应继续坚持的处理原则。  
> 项目：`Nuos/clauderuntime`  
> B4 功能提交：`eff80250b0603a8305660e9f2c88d77d5e73b547`  
> B4 发布状态更新提交：`95efbaec4796147657668c4947a0d2088ecc4738`  
> Reference：Claude Code recovered source `2.1.88`  
> 论文：`Dive into Claude Code: The Design Space of Today’s and Future AI Agent Systems`，arXiv:2604.14228v2  
> 状态：B4 的 C2–C5 已完成并验证；C1 跨平台真实隔离、C6 最终机器证据收口未完全完成。

# 0. 总结

B4 的主要价值不是“增加了多少功能”，而是把 B3 后最关键的几个核心缺口从“功能存在但语义不完整”推进到“有真实实现、有专项测试、有部分 source-aligned 证据”。

B4 实际解决了以下几类关键问题：

1. **后台 Agent Resume 原来是假恢复**：只把状态重新标成 running，没有真实重新进入 Agent Loop。
2. **Sandbox 只有接口，没有真实隔离**：B4 在 macOS 上接入了 Seatbelt，并把 foreground/background Bash 都接入 ExecutionBoundary。
3. **进程超时只结束根进程，可能遗留子进程**：统一了 process-tree 生命周期。
4. **MCP transport 成功但 capability discovery 失败时可能留下假连接/旧工具**：统一 terminal cleanup。
5. **Hook timeout 可能留下后台子进程继续修改工作区**：改成整棵进程树终止。
6. **Compact / Context 只有代码，没有清晰对照矩阵**：补了 Compact-5 与 Context-9 文档和专项测试。
7. **不同入口的一致性主要停留在结构层面**：补了 core/server 相同输入的 runtime differential。
8. **测试本身存在“假绿”与环境污染问题**：修复 async test、macOS sandbox 环境、后台通知竞争、custom endpoint 等测试问题。
9. **Parity machine evidence 原来不完整**：新增 callgraph、state-transition、runtime-trace、divergence、scorecard 等控制面资产。

但 B4 也暴露出一个更深层的问题：

> **“专项测试通过”并不自动等于“Source-Aligned 完成”。**

进入 B5 后发现，B4 的一部分 VERIFIED 结论仍存在 source drift，例如 Compact-5、Context-9、Resume durable reconstruction、Scheduler、全 Surface differential 和跨平台 Sandbox。

因此，B4 应被理解为：

> **核心闭环大幅推进完成，但最终 Source-Aligned Closure 尚未完成。**

# 1. C1：Execution Environment / Sandbox / Process Lifecycle

## 1.1 问题：`NoSandboxBackend` 只有接口，没有真实隔离

### 现象

B3 时已有 SandboxBackend / ExecutionBoundary 结构，但默认 backend 仍是：

```text
NoSandboxBackend
provides_isolation = False
```

这意味着：

- 可以判断“要求隔离但当前没有隔离”；
- 可以 fail-closed；
- 但真正执行命令时仍然可能是普通 subprocess；
- 不能宣称已经与 Claude Code 的 sandbox runtime 等价。

### 根因

之前把：

```text
有 Sandbox 接口
```

误认为接近：

```text
有真实 Sandbox
```

实际上两者完全不同。

Claude Code reference 的核心行为是：

```text
settings
→ shouldUseSandbox
→ capability / policy
→ SandboxManager.wrapWithSandbox
→ actual isolated process
```

### B4 解决思路

B4 将问题拆成两层：

1. **先统一 canonical process lifecycle**
2. **再接入真实 OS isolation backend**

### 已完成

#### a. 统一进程树生命周期

新增：

```text
run_process_tree()
```

统一：

```text
launch
→ process group
→ timeout
→ TERM
→ grace period
→ KILL
→ drain stdout/stderr
→ terminal result
```

解决“根 shell 结束，但孙进程继续跑”的问题。

#### b. macOS Seatbelt Backend

新增真实：

```text
MacOSSandboxBackend
```

通过：

```text
/usr/bin/sandbox-exec
```

实现：

- capability probe；
- default-deny profile；
- cwd write scope；
- read/write deny path；
- network default deny；
- `allowAll` 网络能力；
- foreground Bash 接入；
- background Bash 接入；
- filesystem read/write E2E；
- secret scrub E2E。

### 当前遗留问题

#### Linux / Windows

当前非 macOS 仍然：

```text
NoSandboxBackend
```

所以不能写：

```text
R7-07 complete
CCR-12 complete
R5-05 complete
```

#### Domain allowlist

当前：

```text
allowed_network_hosts
```

已经进入 policy 数据结构，但还没有真正形成安全的 OS-level domain enforcement。

不能把：

```text
配置里有 allowedDomains
```

等价成：

```text
运行时已经按域名隔离
```

#### Read policy

macOS backend 仍保留较宽：

```text
(allow file-read*)
```

再用 deny path 收紧。

这和 reference 的完整 filesystem runtime config 仍有差距。

### B5 继续方案

- Linux：Landlock / bubblewrap 或等价可验证 backend；
- Windows：Restricted Token / AppContainer / Job Object / ACL 的可证明组合；
- domain allowlist 必须解决 DNS rebinding / TOCTOU；
- native macOS/Linux/Windows E2E；
- capability unavailable 且 require isolation 时必须 fail-closed。

# 2. C1：Foreground / Background Bash 存在执行边界旁路

## 问题

早期只给 foreground Bash 接 ExecutionBoundary，会出现：

```text
foreground Bash → sandbox
background Bash → raw Popen
```

这相当于同一个 Tool 有两条安全语义。

### 风险

模型只需选择：

```text
run_in_background
```

就可能绕过 foreground sandbox。

### B4 解决方案

background Bash 同样构造：

```text
SandboxRequest
→ execution_boundary.prepare_sandbox()
→ sandbox_command_argv()
→ background task registry
```

同时保留 background subsystem 自己的：

- task id；
- output file；
- reaper；
- completion notification；
- stop lifecycle。

### 原则

> Sandbox 只能改变“如何 launch”，不能夺走 background task manager 对 lifecycle 的 ownership。

# 3. C1：ProcessPolicy / timeout / abort 不统一

## 问题

B3 时真实 kill-tree 逻辑散落在：

- Bash；
- Hook；
- shell_platform；
- background runner；

没有形成统一 process contract。

### 直接后果

不同路径可能出现：

```text
timeout → kill root only
```

或：

```text
ESC → kill tree
```

导致：

- orphan child；
- timeout 后仍写文件；
- surface interrupt 行为不一致。

### B4 解决方案

把核心行为统一为：

```text
popen_tree_kwargs()
kill_process_tree()
TERM → grace → KILL
```

并逐步接入：

- Sandbox；
- foreground Bash；
- background Bash；
- Hook executor。

### 尚未完全解决

`DefaultProcessPolicy` 仍需要进一步形成真正 canonical execution policy，而不是只共享 helper。

# 4. C2：后台 Agent Resume 是“假恢复”

## 4.1 原问题

B3 的 `resume_agent_background()` 主要做：

```text
terminal state
→ race-safe claim
→ read transcript
→ register_async_agent
```

但是并没有真正调用：

```text
run_agent()
```

所以用户看到：

```text
running
```

实际上没有继续推理。

### 业务后果

- SendMessage 看起来发送成功；
- Agent 看起来恢复；
- 实际没有模型执行；
- 用户恢复 prompt 不会被真正处理。

这是典型：

```text
state changed
!=
behavior resumed
```

## 4.2 B4 解决方案

新增真实重入：

```text
terminal
→ claim
→ transcript replay
→ hydrate typed messages
→ rebuild RunAgentParams
→ register fresh running state
→ task_manager.start()
→ run_agent()
→ write transcript
→ complete / fail state
→ notification
```

并处理：

- concurrent resume race；
- pending message；
- transcript corruption；
- missing dependency；
- completion/failure notification。

### 一个关键安全改进

如果恢复所需运行依赖不存在：

```text
resume_run_params is None
```

则明确失败：

```text
live resume dependencies are unavailable
```

而不是继续展示假 running。

# 5. C2：Resume 真重入仍不是完整 Durable Resume

## 问题

B4 修复之后，resume 依赖：

```text
LocalAgentTaskState.resume_run_params
```

该对象是内存对象，不持久化。

源码本身也明确说明：

```text
服务进程重启后必须重新构建实时依赖
```

### 意味着

当前已实现：

```text
same-process true resume
```

但尚未完整实现：

```text
process-restart durable resume
```

### Claude Code reference 更完整的行为

Reference 会从：

```text
transcript + metadata + current ToolUseContext
```

重新构建：

- sanitized messages；
- content replacement state；
- worktree；
- agent definition；
- model；
- permission context；
- tool pool；
- system prompt；
- background lifecycle。

### B5 解决方案

不再持久化整个 RunAgentParams 对象，而是持久化**可重建元数据**：

```text
agent type
description
worktree
lineage
content replacements
transcript path
tool/runtime identity hints
```

恢复时使用当前 runtime factory 重新组装 dependency graph。

# 6. C3：Compact-5 只有“结构对齐”，存在 Source Drift

## 6.1 B4 当时解决了什么

B4 新增：

```text
compact-5-matrix.yaml
```

明确记录：

1. Tool Result Budget
2. Snip Compact
3. Microcompact
4. Context Collapse
5. AutoCompact

并补：

- execution order；
- default microcompact no-op；
- token accounting；
- early exit；
- layer failure continuation；
- durable state。

专项测试通过。

## 6.2 后续发现的问题

### 问题 A：`snip_compact()` 实际仍是 stub

当前实现：

```python
return list(messages), 0
```

也就是说：

```text
Layer 名称存在
!=
真实 behavior 存在
```

### 问题 B：Python 增加了全局 `early_exit_tokens`

Python 可以：

```text
Layer 1 saved enough
→ return immediately
→ skip later shapers
```

而 Claude Code 2.1.88 `query.ts` 的实际 control flow 是连续执行：

```text
tool result budget
→ snip
→ microcompact
→ context collapse
→ autocompact
```

后面模块自己根据 gate/no-op 决定是否生效。

### 问题 C：Microcompact gate 位置不同

Reference：

```text
每轮调用 microcompactMessages()
→ 内部决定 time-based / cached / no-op
```

Python：

```text
if mc_enabled:
    调用 microcompact
else:
    整个 stage 不进入
```

这是调用结构差异。

### 问题 D：测试 oracle 是项目自己写的 snapshot

当前 parity test 使用：

```text
src/reference_data/ts_compression_layers.json
```

而这个文件本身是项目人工整理的。

如果 snapshot 写错：

```text
Python tests 仍然全部绿
```

### B5 解决原则

> Reference oracle 必须能追溯到 source symbol / call edge / hash。

不能：

```text
自己写 reference_data
→ 再测试自己实现符合 reference_data
→ 宣称 source aligned
```

# 7. C3：Context-9 中 Path Rules 分类错误

## B4 目标

建立 9 类 context source：

1. System Prompt
2. Environment
3. Project Instructions
4. Path Rules
5. Auto Memory
6. Tool Metadata
7. Conversation
8. Tool Results
9. Compact Summaries

## 暴露的问题

`context-9-matrix.yaml` 将：

```text
path_rules
```

映射成：

```text
src/permissions
insertion = permission_context
```

这是语义分类错误。

### Reference 实际含义

论文与 Claude Code 源码中的 Path-scoped Rules 指：

```text
.claude/rules/*.md
paths: ...
```

它属于：

```text
Context Assembly
```

而不是：

```text
Permission System
```

### 当前 Python 情况

`clawcodex_md.py` 已经支持：

- rules 目录；
- frontmatter `paths:`；
- `conditional_rule` 参数；
- include；
- project/user/local memory。

但是当前 production loading path 主要调用：

```text
conditional_rule=False
```

没有充分证据证明：

```text
Read file A
→ lazy match paths rule
→ inject rule once
→ next model request sees rule
```

### B5 解决方案

增加真正 E2E：

```text
read src/foo.py
→ resolve canonical path
→ match .clawcodex/rules/python.md
→ inject context
→ same rule does not duplicate
→ unrelated file does not trigger
```

> **测试环境要隔离生产配置，而不是为了测试通过削弱生产安全行为。**

# 9. C4：MCP transport 成功 ≠ MCP capability 可用

## 原问题

MCP reconnect 可能出现：

```text
transport connected
→ list_tools() failed
```

但 runtime 仍留下：

```text
ConnectedMCPServer
client
wrapped tools
```

### 风险

后续 tool pool 可能把：

```text
实际已经不可调用的 MCP tool
```

继续暴露给模型。

## B4 解决方案

统一 `_install_connection()`：

```text
connect
→ list_tools
→ wrap tools
→ publish connected state
```

只有完整 capability discovery 成功后才发布。

任何 discovery exception：

```text
clear client
clear tools
close fresh client
publish FailedMCPServer
rethrow
```

# 10. C4：MCP shutdown 后遗留 stale capability

## 问题

进一步回归后发现：

```text
close_all()
```

只关闭 client，却还保留：

```text
Connected state
wrapped tools
```

这意味着：

```text
transport 已死
但 tool capability 还在
```

### B4 解决方案

shutdown 变成真正终态：

```text
close client
→ clear _tools
→ clear _state
→ snapshot/get_tools/all_tools 不再暴露 capability
```

### 设计原则

> Capability 的可见性必须由“当前可调用状态”决定，而不是“曾经连接成功”。

# 12. C5：Hook timeout 只杀 shell root

## 问题

Hook 可以执行 shell command。

旧 timeout 行为：

```text
process.kill()
```

只结束 shell root。

如果 hook 启动：

```text
shell
└── background child
```

child 可能继续：

- 写文件；
- 网络请求；
- 修改 workspace。

调用方却已经收到 timeout。

## B4 解决方案

Hook 改成：

```text
popen_tree_kwargs()
→ timeout
→ kill_process_tree()
→ TERM
→ grace
→ KILL
→ drain
```

并增加测试：

```text
timeout 后 child 不能继续产生文件副作用
```

### 关键原则

> 错误返回不是安全证明。必须验证副作用没有继续发生。

# 13. C5：Cross-Surface 之前只有“结构一致”

## 原问题

之前所谓：

```text
surface parity
```

很多是检查：

- import；
- function name；
- shared module；
- source structure。

这不能证明：

```text
同一用户输入
→ 同一 runtime decision
→ 同一 terminal
```

## B4 解决方案

增加 deterministic provider：

```text
same input
→ core run_query_as_agent_loop
→ server DirectConnect
```

比较：

- response text；
- terminal；
- usage；
- num_turns。

这是一个真正 runtime differential。

## 当前不足

还只覆盖：

```text
core
vs
server
```

没有真正覆盖：

- CLI；
- TUI；
- Desktop；
- IDE / VSCode。

### B5 方案

为每个官方声明支持的 Surface 跑相同 scripted trace。

# 14. B4 测试体系自身发现的问题

B4 在扩大回归时发现多项“测试自己有问题”。

## 14.1 Async unittest 假绿

部分 async unittest 之前没有被正确 await。

### 解决

修复测试执行方式，保证协程真正运行。

### 原则

```text
test reported PASS
!=
tested code actually executed
```

---

## 14.2 Hook 新增 subprocess 参数后旧 mock 不兼容

生产代码增加：

```text
process group / tree kwargs
```

旧测试 mock 没接受新参数。

### 解决

修测试，不回滚生产生命周期安全增强。

---

## 14.3 Sandbox test 意外使用真实 macOS backend

部分单测本来只想测试逻辑，却因为当前机器是 macOS 而走了真实 Seatbelt。

### 解决

测试显式选择：

```text
NoSandboxBackend
```

或明确指定 backend。

### 原则

区分：

```text
unit policy test
```

和：

```text
native E2E sandbox test
```

---

## 14.4 Background notification race

其他后台线程可能先消费通知。

### 解决

测试不再依赖共享队列“下一条一定是我的”，改成直接记录/截获本次发送结果。

### 原则

并发测试不能依赖全局 queue 的偶然顺序。

current HEAD CI is green

# 18. B4 中最值得保留的解决问题方法

## 方法 1：把“状态变化”和“行为发生”分开验证

Resume 的问题说明：

```text
state = running
```

不代表：

```text
Agent actually running
```

未来所有 lifecycle 都要用 runtime trace 验证。

---

## 方法 2：安全边界分层，不互相代替

B4 反复验证了：

```text
Permission
!= Hook
!= Workspace Guard
!= Sandbox
!= Network
!= Process Lifecycle
```

一个层通过，不能认为其他层已经安全。

---

## 方法 3：先消除 bypass，再做能力增强

例如 Bash：

```text
foreground sandboxed
background unsandboxed
```

这种状态优先级高于新增更复杂的 sandbox policy。

---

## 方法 4：terminal state 必须清理 capability

MCP：

```text
transport closed
```

必须同步：

```text
tools hidden
state cleared
client cleared
```

---

## 方法 5：测试必须验证“副作用没有发生”

尤其：

- sandbox；
- hook timeout；
- secret scrub；
- write deny；
- network deny。

不能只断言：

```text
return code != 0
```

必须进一步断言：

```text
file not created
socket not connected
secret not visible
child no longer running
```

---

## 方法 6：发现测试假绿，要修 test harness，不掩盖

B4 修复 async fake-pass、mock 参数、环境污染、queue race 都属于正确做法。

---

## 方法 7：Source-Aligned 不以“测试数量”判断

B4 最重要的后验经验：

```text
10144 tests passed
```

仍然可能同时存在：

- source drift；
- taxonomy drift；
- stale machine evidence；
- wrong reference snapshot；
- platform gap。

所以最终标准必须是：

```text
source
→ symbol
→ call edge
→ implementation
→ runtime trace
→ differential
→ machine evidence
```
