# 核心修订：分级 Reference 对齐

> **凡是 Claude Code recovered source 能够确定的功能、模块、函数契约、关键控制行为，仍然以 Claude Code 2.1.88 为对齐目标；只有 Reference 具体实现无法确定或恢复不完整的部分，才降低为“核心功能一致 + Python-native 实现 + 差异透明记录”。**

B6 不是“所有模块都只要求功能类似”，而是：

```text
Reference 可确定
→ 必须优先对齐

Reference 部分可确定
→ 已确定部分必须对齐
→ 未确定部分允许功能类似

Reference 无法确定
→ 只要求核心功能/用户目标一致
→ 必须记录不确定性与 Python 实现

Product Extension
→ 明确与 Reference 分离
→ 不得伪装为 Claude Code 原有行为
```

| Reference 证据等级 | 定义 | 开发要求 |
|---|---|---|
| `R1_CONFIRMED` | 源文件、symbol、函数体/关键控制流能够确认 | **必须对齐功能、模块职责、关键行为和已知安全/状态语义** |
| `R2_PARTIALLY_CONFIRMED` | call-site、接口、返回契约或部分逻辑可确认，但实现体不完整 | **已确认部分必须对齐；未知部分允许 Functional Adaptation** |
| `R3_UNKNOWN` | recovered source 无法确认具体实现，只能确认功能名称/高层目的 | **只要求核心功能一致，并明确标记 UNKNOWN_REFERENCE** |
| `R4_PRODUCT_EXTENSION` | ClaudeRuntime 自己新增的功能或增强 | **独立记录，不计作 Claude Code 对齐能力** |

# 1. 为什么调整目标

此前 B4/B5 的目标是接近严格的 Source-Aligned：不仅要求功能存在，还要求关键控制流、状态转换、权限顺序、恢复语义、平台行为和证据链与 Claude Code 2.1.88 recovered source 尽可能一致。

这一标准适合做“高保真复刻/兼容性研究”，但会把大量开发时间投入到：

- Node/TypeScript 与 Python 运行时差异；
- recovered source 未完整恢复的函数；
- 平台专用 sandbox；
- file watcher / owner lock / transport 细节；
- source-level call-edge 证明；
- 全 Surface differential；
- machine evidence 完整闭环。

现在目标调整为：

> **ClaudeRuntime 是一个以 Claude Code 2.1.88 为主要设计参考的 Python Agent Runtime；优先实现相同或相近的核心功能与用户体验，不再要求内部实现路径逐项一致。**

---

# 2. 新的“完成”定义

一个功能可以标记 `FUNCTIONAL_COMPLETE`，只需要满足：

1. 用户可触发该功能；
2. 主要业务目的与 Reference 相同或相近；
3. 正常路径可运行；
4. 关键失败路径有明确处理；
5. 必要安全边界没有被绕过；
6. 有直接相关测试；
7. **源码差异记录已经填写。**

不再要求：

- 文件结构相同；
- 类名相同；
- control-flow 完全相同；
- call-edge 完全相同；
- 状态机逐状态相同；
- 所有平台使用相同底层 primitive；
- 全部 Reference symbol 可映射；
- 只有 EXACT 才算完成。

---

# 3. 新状态体系

以后开发进度使用以下状态：

```text
FUNCTIONAL_COMPLETE
    核心功能完整可用；与 Reference 的主要用户目标相似。

FUNCTIONAL_ADAPTATION
    功能目标相同，但采用 Python/平台原生的不同实现；差异已记录并接受。

LIMITED
    功能可用，但存在明确范围限制。

DEFERRED_REFERENCE_DETAIL
    Reference 有更细行为，但当前不影响主要功能，延期实现。

UNKNOWN_REFERENCE
    recovered source 无法确认；禁止伪造“Reference 就是这样”。

MISSING
    核心功能尚未实现。
```

其中 `FUNCTIONAL_COMPLETE` 与 `FUNCTIONAL_ADAPTATION` 均可以计入 B6 功能完成度。

---

# 4. 差异允许范围

允许以下差异，只要记录清楚：

- Python async / thread / subprocess 实现不同；
- Python-native 数据模型不同；
- scheduler 使用 snapshot/restore，而不是完全复刻 file watcher；
- Resume 使用 Python metadata/runtime factory，而不是复刻 TypeScript 对象组装方式；
- sandbox 使用不同 OS primitive；
- UI/Surface 的事件 envelope 不同；
- Context/Compact 内部算法不同，但达到相近目的；
- recovered source 缺失时采用保守实现；
- 为安全、可维护性、跨平台性而做的实现简化。

---

# 5. 不允许因为“降低要求”而取消的底线

功能类似不等于可以牺牲安全。

以下仍是硬约束：

```text
Permission deny 不得被绕过
Workspace/path guard 不得无故绕过
Sandbox required 时不可静默退化成 unrestricted execution
Hook timeout 后不可留下继续执行的高风险 child process
Resume 不得恢复 API key / 临时权限 / session temporary trust
MCP 已断开后不得继续暴露 stale callable tools
Background execution 不得成为 foreground 安全边界的旁路
明显失败不得伪装成 running/completed
```

# 6. Reference 的新角色

Reference 从“验收 oracle”调整为：

```text
设计参考
功能清单来源
行为比较基准
差异说明来源
```

不是每个 Reference 细节都必须复刻。

论文对 Claude Code 2.1.88 的结构性描述仍用于维护：

- 7 个核心组件；
- 5 层 subsystem architecture；
- 五层 context compaction；
- permissions、hooks、MCP、skills、plugins、subagents、session storage 等主要功能域。

CCR-14 继续作为 ClaudeRuntime 内部工程分类，但必须明确：**CCR-14 是工程归纳，不是论文官方 14 项分类。**
